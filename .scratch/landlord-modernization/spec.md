# Spec: landlord 现代化改造

Status: done

## Problem Statement

`src/landlord` 是我早年学 C 时写的斗地主实现，刚从独立仓库迁入 cmg。它能跑完 10000 局 AI 对战，但我没法信任它，也没法安全地改它：

- **对局不校验规则。** 规则 module（牌型识别、大小比较）没有接进出牌路径，对局完全信任 AI 交回的牌。实测 10000 局、131997 手出牌里：7991 手被规则 module 判为非法，其中 7980 手是规则 module 自己的缺陷（不认以 A 结尾的顺子、连对、飞机），其余是 AI 的缺陷（同一张牌出现两次）以及规则表缺项（三组以上的飞机带对子）；373 手 AI 标注的牌型与实际不符（三带一被标成三张）；93 次压牌其实压不过上一手。
- **结果不可复现。** 开局时用未初始化的随机数状态洗牌，第一局和后续局使用不同的 AI，无人叫分时重发的是未洗的牌。同一套代码两次构建跑出 7652 和 7650 两个不同的地主胜局数。
- **有确定的内存缺陷藏在没被调用的路径里。** 内存追踪的重分配在释放后读取，随机数的数组播种越界写，牌组的弹出、压牌搜索里各有一处差一。
- **没有测试。** 入口程序只是打印胜负数的基准，没有任何断言。
- **编译器帮不上忙。** 严格选项下有 96 条警告，内部函数全部带外部链接，几乎没有 `const`，常量全是宏，AI 的 interface 是 `void *`。
- **结构让改动四处扩散。** 「什么压得过什么」写了三份；拆牌和评估是同一逻辑的两份实现；AI 直接改写局面；通用容器没有挡住任何东西，所有权靠调用方记忆。

## Solution

把 landlord 改造成一个我敢改、改了能立刻知道对不对的子项目：

- `make test` 会运行 landlord 的自检，规则有表格化用例，整局对战有按种子固定的基线。
- 对局中每一手牌都经过规则 module 校验，非法出牌和压不过的牌不可能进入牌局。
- 同一个种子在任何机器、任何构建档位下得到同一局牌。
- 严格警告选项下零警告，ASan/UBSan 下干净。
- 规则、拆牌、压牌搜索、Game、AI 各是一个 deep module，interface 小而明确。
- 代码遵循 cmg 的命名与风格约定。

术语（landlord 尚无 GLOSSARY.md，本 spec 统一使用）：

| 术语 | 含义 |
|---|---|
| 牌型 | 一手合法的出牌及其类别（单张、对子、三带一、顺子、连对、飞机、炸弹、王炸等） |
| 规则 module | 判定一组牌是不是合法牌型、两手牌谁大 |
| 拆牌 | 把一家的手牌分解成若干牌型；「几手能出完」是拆牌结果的手数 |
| 压牌搜索 | 给定手牌和上一手，找出所有能压过它的牌型 |
| 局面 | 一局牌在某一时刻的全部状态：三家手牌、上一手、谁出的、叫分、身份 |
| 叫分 | 开局争地主的环节 |
| 基线 | 固定种子范围内每一局的结果摘要，用来确认重构没有改变行为 |

## User Stories

1. As 仓库所有者, I want `make test` 同时运行 landlord 的自检, so that 我改完代码能用一条命令知道有没有改坏。
2. As 仓库所有者, I want 规则有一张「牌 → 牌型」的用例表, so that 我能一眼看出支持哪些牌型，并且随手加用例。
3. As 仓库所有者, I want 以 A 结尾的顺子、连对、飞机被识别为合法牌型, so that 规则 module 与斗地主的实际规则一致。
4. As 仓库所有者, I want 三组及以上的飞机带对子被识别为合法牌型, so that 规则表没有缺项。
5. As 仓库所有者, I want 含重复牌的出牌被判为非法, so that AI 的缺陷不会悄悄进入牌局。
6. As 仓库所有者, I want 对局中每一手出牌都由规则 module 校验, so that 规则写错时 10000 局对战会立刻失败。
7. As 仓库所有者, I want 每次压牌都被确认确实大于上一手, so that 牌局的进行是可信的。
8. As 仓库所有者, I want AI 交回的牌型标注由规则 module 重新判定, so that 三带一不会被当成三张。
9. As 仓库所有者, I want 同一个种子永远得到同一局牌, so that 我能复现任何一局并对比改动前后的结果。
10. As 仓库所有者, I want 每一局使用相同的 AI 配置, so that 统计数字描述的是同一件事。
11. As 仓库所有者, I want 无人叫分时重新洗牌再发, so that 重发的牌仍然是随机的。
12. As 仓库所有者, I want 一份按种子记录的基线, so that 任何重构都能证明自己没有改变行为。
13. As 仓库所有者, I want 行为发生变化时基线被显式更新并写明原因, so that 我能区分「修了 bug」和「改坏了」。
14. As 仓库所有者, I want 严格警告选项下零警告, so that 新引入的问题会被编译器当场指出。
15. As 仓库所有者, I want 自检在 ASan/UBSan 下干净, so that 内存缺陷不再藏在没被调用的路径里。
16. As 仓库所有者, I want 已知的越界、释放后使用和差一缺陷被修掉或随死代码一起删除, so that 代码里没有已知的未定义行为。
17. As 仓库所有者, I want 「什么压得过什么」只写在规则 module 一处, so that 改规则只需要改一个地方。
18. As 仓库所有者, I want AI 只负责决定叫几分、出哪手牌, so that Game 能保证局面的不变量。
19. As 仓库所有者, I want AI 拿到的是只读的局面, so that AI 不可能改坏牌局。
20. As 仓库所有者, I want 两个 AI 的差异只剩下拆牌和评估方式, so that 压牌决策的逻辑只有一份。
21. As 仓库所有者, I want AI 的 interface 带真实类型而不是 `void *`, so that 编译器能检查调用是否正确。
22. As 仓库所有者, I want 拆牌结果的手数就是评估值, so that 拆牌和评估不可能不一致。
23. As 仓库所有者, I want 拆牌的结果恰好覆盖手牌且每一手都是合法牌型, so that 拆牌的正确性可以被自动检查。
24. As 仓库所有者, I want 搜索式拆牌的手数不多于标准拆牌, so that 「高级」AI 确实不比标准 AI 差。
25. As 仓库所有者, I want 压牌搜索返回的每一手都确实压得过上一手, so that 搜索和规则不会各说各话。
26. As 仓库所有者, I want 按点数查询和取牌而不是自己算数组下标, so that 「必须先排序」不再是调用方要记住的前提。
27. As 仓库所有者, I want 牌型列表是值类型且容量有上限, so that 不存在谁来释放的问题。
28. As 仓库所有者, I want 自写的内存追踪被删掉, so that 标准库函数名不再被宏覆盖，内存检查交给 sanitizer。
29. As 仓库所有者, I want 没有调用方的代码被删掉, so that 读代码时不必分辨哪些是活的。
30. As 仓库所有者, I want 内部函数只有内部链接, so that 每个 module 的 interface 就是头文件里声明的那些。
31. As 仓库所有者, I want 只读参数标注为 `const`, so that 函数会不会改我的数据从声明就能看出来。
32. As 仓库所有者, I want 点数、花色、牌型、阶段用枚举表示, so that 调试器显示名字、`switch` 能查漏。
33. As 仓库所有者, I want 日志开关和花色显示方式是构建选项, so that 切换它们不需要改源码。
34. As 仓库所有者, I want 标识符遵循 cmg 的命名约定, so that landlord 读起来和仓库其他子项目一致。
35. As 仓库所有者, I want 基准程序和自检程序是两个独立目标, so that 跑统计和跑测试互不干扰。
36. As 仓库所有者, I want 子项目 README 说明 module 划分、如何运行和如何更新基线, so that 以后回来能快速接上。
37. As 执行工单的 agent, I want 每个阶段有明确的验收命令和预期结果, so that 我能自己判断是否完成。
38. As 执行工单的 agent, I want 每个阶段声明它是否允许改变行为, so that 我知道基线不一致时是该修代码还是该更新基线。
39. As 执行工单的 agent, I want 阶段之间的依赖顺序是明确的, so that 我不会在安全网就位之前动结构。
40. As 执行工单的 agent, I want 领域术语有统一定义, so that 我给 module 和函数起的名字与 spec 一致。
41. As `make test` 的运行者, I want landlord 自检在几秒内跑完, so that 它不会拖慢整个仓库的测试。
42. As `make test` 的运行者, I want 失败时打印出种子和出错的那手牌, so that 我能直接复现。

## Implementation Decisions

**总体原则**

- 斗地主规则保持不变；只修正「识别错了」的情况（A 结尾的链、飞机带对子缺项）。
- 不追求 AI 更强。AI 的决策逻辑只在修缺陷和消除重复时改动。
- 每个阶段是一次独立的、可验证的提交序列；阶段结束时自检通过，基线要么一致，要么带原因更新。
- 这是「大 plan」。拆成可执行工单时每个阶段一张，由后续的工单拆分步骤完成。

**阶段 0 · 测试入口**

- 新增 landlord 自检目标并接入 `make test`；现有入口程序改为基准目标，不再承担测试职责。
- 给 landlord 目标打开严格警告选项，并提供一个 sanitizer 构建方式供自检使用。

**阶段 1 · 确定性**

- 随机数状态在首次使用前初始化；每一局使用同一套 AI 配置；无人叫分时重新洗牌再发。
- 本阶段允许改变对局结果。

**阶段 2 · 基线**

- 在 Game 的整局 seam 上，对固定种子范围记录每局的结果摘要（胜者、地主、出牌序列的摘要值），作为基线提交进仓库。
- 基线文件是产物：由自检程序的一个模式重新生成，不手改。

**阶段 3 · 零行为变化的清理**

- 内部函数改为内部链接；去掉下划线开头的保留标识符；日志宏改为可变参数形式；函数声明补全原型；修掉全部警告。
- 删除死代码：多线程试验段、牌堆的回收区、未使用的常量和函数、空壳 AI 函数。
- 修掉不影响对局结果的缺陷：牌组弹出的差一、压牌搜索的多读、打印函数的越界、取尾宏的拼写。
- 基线必须保持一致。

**阶段 4 · 规则 module 接入出牌路径（架构候选 1）**

- 规则 module 补齐：A 结尾的链；任意组数的飞机带单、带对；拒绝含重复牌的输入。
- 牌型识别不再修改传入的牌。
- Game 增加出牌入口：收到一手牌后由规则 module 判定牌型与是否压过上一手，不合法则拒绝。牌型以规则 module 的判定为准，不采信 AI 的标注。
- 压牌搜索以规则 module 的比较为准，删除它自带的比较逻辑和 AI 里的炸弹特判副本。
- 修掉因此暴露的 AI 缺陷（重复牌、三带一标注错误、统计带牌时漏掉最后一手）。
- 本阶段允许改变对局结果；基线更新并写明原因。

**阶段 5 · Game 与 AI 的 seam（架构候选 2）**

- AI 的 interface 收窄为：给一份只读局面，返回一个决定（叫几分 / 出哪手牌或不出）。
- 扣牌、更新上一手、记录出牌、重算拆牌都由 Game 完成。
- AI 只能看到自己的手牌和公开信息（各家剩余张数、已出的牌、身份）。当前「队友牌更少就不压」的判断只用到剩余张数，可以保留。
- 两个 AI 共享同一份压牌决策，差异只是注入的拆牌与评估方式。
- 用前向声明解开玩家与 Game 的头文件互相依赖，去掉 `void *`。
- 基线必须保持一致。

**阶段 6 · 拆牌与压牌搜索（架构候选 3）**

- 现在的单个大文件拆成两个 module：拆牌（手牌进，牌型列表出）、压牌搜索（手牌加上一手进，候选列表出）。
- 评估值定义为拆牌结果的手数，删除独立的评估实现。
- 搜索上下文（点数计数、正序、逆序）在一处构造，对 module 外不可见。
- 基线必须保持一致；如果合并两份实现时发现它们原本就不一致，按拆牌的结果为准并更新基线、写明原因。

**阶段 7 · 手牌表示（架构候选 4）**

- 手牌 module 内部始终维护点数计数；对外提供按点数查询、按牌组增减的操作；排序和下标不外露。
- 没有调用方或只是一两行转发的操作删除。
- 字符串与牌的互转补齐结尾与边界处理。
- 基线必须保持一致。

**阶段 8 · 容器与内存（架构候选 5）**

- 牌型列表改为容量有上限的值类型（一家最多 20 张牌，拆牌手数有界）。
- 搜索树成为拆牌 module 的内部细节；通用链表与树 module 删除。
- 删除自写的内存追踪，内存检查交给 sanitizer。
- 随机数的数组播种没有调用方，随死代码删除；两份洗牌实现合并为一份。
- 基线必须保持一致。

**阶段 9 · 现代化与命名**

- 只读参数加 `const`；点数、花色、牌型、阶段、状态改为枚举；牌型的位域操作改为结构化表示；规格表改为结构体数组。
- 日志开关与花色显示方式改为构建选项；公共头文件只包含自己需要的标准头。
- 标识符统一为 cmg 约定：snake_case、类型 `xxx_t`、函数带 module 前缀、宏全大写带前缀。项目记忆里写着「子项目不追求统一风格」，这次是所有者明确要求全做，因此对 landlord 例外。
- include guard 统一；修正注释与标识符里的拼写错误。
- 更新子项目 README；新建 landlord 自己的 GLOSSARY.md 收录上面的术语，并在根目录 GLOSSARY-MAP.md 里登记。
- 基线必须保持一致。

## Testing Decisions

- **好的测试只检查外部行为**：给定输入牌或种子，检查牌型、比较结果、对局结果；不检查内部数据结构、不检查调用次数。
- **两个 seam，都是现有的：**
  - *规则 interface*（一组牌 → 牌型；两手牌 → 大小）。表格化断言，首批用例是已实测的那几手：`34567` 合法，`TJQKA`、`QQKKAA`、`KKKAAA` 目前被误判；加上 15 张的飞机带对子、含重复牌的输入。
  - *Game 的整局 interface*（种子 → 一局牌）。两种检查：不变量（每一手合法、每次压牌更大、牌的总数守恒、胜者手牌为空）和基线对比（每局摘要与记录一致）。
- 拆牌与压牌搜索的性质（覆盖手牌、每手合法、搜索式不多于标准式、候选都压得过）在阶段 6 之后通过它们各自的 interface 断言；在此之前由整局不变量间接覆盖。
- **不引入测试框架**，沿用仓库做法：assert 自检的可执行程序。
- **Prior art**：dsaac 的 assert 自检；texas 的测试目标把「参考实现与快速实现全量对拍」和基准程序分成两个目标，landlord 的基线对比与自检/基准拆分照此办理。
- 自检默认跑一个较小的种子范围以保持几秒内完成；完整的 10000 局留给基准目标。
- 失败时打印种子与出错的那手牌。

## Out of Scope

- 提升 AI 棋力、新的 AI 策略、README 里原有的 TODO（残局策略、提示、更好的叫分）。
- 人类玩家、交互界面、网络对战。阶段 5 之后可以接入，但不在本 spec 内实现。
- Lua 与 JavaScript 绑定（已决定不迁入）。
- 多线程模拟。
- 仓库里的其他子项目；不与 dsaac 共享容器或内存追踪代码。
- 性能优化。只要求自检时间可接受，不设性能目标。

## Further Notes

- 审计时的实测数据（迁入时的代码）：严格选项下 96 条警告；ASan/UBSan 下 10000 局对战无报告；131997 手出牌中 7991 手被规则 module 判非法（7980 手为 A 结尾链的误判），373 手牌型标注不符，93 次压牌未通过比较。
- 阶段 1 和阶段 4 之后基线会变，这是预期的；其余阶段基线变了就是改坏了。
- 阶段 3 可以与阶段 1、2 之后的任何阶段并行推进，但放在结构调整之前做，能让后面的改动一直处在零警告之下。
- 阶段 8 依赖阶段 6；阶段 9 的命名改动放在最后，避免与结构调整的 diff 混在一起。
- 提交信息用 Conventional Commits；每个阶段结束时 `make fmt`、`make test` 通过。
